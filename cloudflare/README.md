# Cloudflare Workers Free: isolated media-free configuration

Status: IMPLEMENTED for QA only. Production, DNS, merges, paid resources and real-media publication are not authorized by these commands. The templates name only the existing three synthetic QA Workers in the verified Free account. No default Production environment, custom routes, schedules, R2, KV or queues are configured. Public endpoints and Preview URLs default to disabled.

Use Linux (or an isolated Linux build container) for HQ OpenNext builds. Tool dependencies are independently locked under tools/cloudflare; run npm ci --ignore-scripts --prefix tools/cloudflare and npm audit --prefix tools/cloudflare --audit-level=low before building. The narrow adm-zip and glob overrides correct toolchain advisories; no app dependency waiver or audit fix is used. Do not install the platform migration/autoconfigure command.

Prepare a fresh tracked-source media-free input with npm run release:prepare -- .media-free-release-<unique-name>, then work inside that directory. Install the app with npm ci --ignore-scripts and the separately locked toolchain as above. HQ build inputs are only NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY; Builder equivalents are VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY. Public receives neither. Supply only disposable backend public settings. The wrapper builds from an explicit environment allowlist; service-role, mail, Cloudflare and unrelated ambient credentials are excluded from build processes.

Run npm run cf:build -- hq (OS), public or builder (Public repository). The checked-in wrapper creates the generated root wrangler.qa.json and, for HQ, open-next.config.ts and a package link into the isolated toolchain. It uses dummy caches and disables route preloading; durable cache behavior and Production capacity remain unaccepted. App and toolchain audits, full tests/types/lint, bundle dry run and artifact scans are required before any upload. npm run cf:dry-run -- <lane> performs no upload. Raw source without a prepared marker is rejected.

Only after the already scoped QA credential/access approval, send disposable backend values through stdin to Wrangler secret bulk using --config wrangler.qa.json. Runtime settings: EVENTSIBLE_CLOUDFLARE_CONTEXT=qa, EVENTSIBLE_CLOUDFLARE_APP_ORIGIN matching the exact lane URL; backend URL/anonymous key and SUPABASE_SERVICE_ROLE_KEY only on HQ/Builder; notification dry-run settings true and no mail provider key. The checked-in templates contain only non-secret QA origins/context. Never add a service-role value to vars, VITE_ or NEXT_PUBLIC_. Browser and server backend origins must match.

npm run cf:deploy:qa -- <lane> keeps public endpoints disabled. Add --expose-qa only during the approved synthetic QA window. No command can select a Production worker or DNS route. Navigate between the compiled exact Public/Builder QA origins; canonical SEO origins stay unchanged. Auth requires the exact configured Builder QA origin and rejects unknown contexts, lookalikes, paths and live-domain fallback even when stale Vercel/Netlify metadata exists. HQ forces notifications to dry-run for every Cloudflare context and suppresses the Netlify scheduler. External social, contact and ECC links are outside QA acceptance and must remain blocked by the test browser.

Freeze exact uploaded version IDs, source hashes and media-free manifests. Rehearse a synthetic canary and rollback to those exact versions, then repeat Owner save/publish/restore, Public Power/Classic read, Staff denial and Builder submit/replay/no-booking. A Worker rollback does not restore a database. Do not reuse prior temporary gateway URLs or restore historical encrypted disposable bindings against a new backend.

Cleanup: npm run cf:disable:qa -- <lane> disables workers.dev and Preview URLs on the named QA worker; confirm HTTP 404 and no active routes. Remove active privileged runtime bindings; after version rollback Cloudflare may require deploying the latest QA artifact with endpoints disabled before secret edits. Revoke temporary OAuth, stop only the named disposable backend/gateway, preserve the original local CI stack and all original media. Historical encrypted bindings may remain in retained QA versions; do not claim they were purged.

Acceptance evidence is source/head specific. Final hosted checks and isolated CI are required after this integration. Remaining Production gates: supported capacity/load and caching, complete Auth callback/provider coverage, explicit Production environment/context design, backup/restore rehearsal, final reviewed heads and separate merge/schema/environment/DNS/media authorities.

References: https://opennext.js.org/cloudflare/get-started , https://developers.cloudflare.com/workers/configuration/secrets/ , https://developers.cloudflare.com/workers/wrangler/environments/ .

HQ QA Auth verification uses a generated .open-next/qa-worker.js wrapper with a fresh AsyncLocalStorage store for each outer HTTP request. Proxy and the server data layer both retain getUser checks. Only identical configured-backend GET /auth/v1/user requests with matching headers share the fresh Auth-server response within that request; failures, mutations and other backend routes are not reused. No store exists outside the QA wrapper. Token refresh, role/capability checks, RLS and publishing RPC authorization remain unchanged. The QA response exposes only a numeric verification count, never identity or credential data. Concurrent Owner/Staff isolation and a new live verification on every request are required acceptance checks. This does not enable private page caching or approve Production use.

For prepared HQ QA builds only, the wrapper temporarily generates the Edge middleware filename/export from the complete proxy source, then restores the original input in a finally block. The generated Edge manifest and restored source are verified before upload. This avoids OpenNext 1.20.13's experimental/unmaintained Node.js middleware path. Next 16 still supports the Edge convention but emits a deprecation notice, so future framework/adapter compatibility remains a gate. The ordinary Production source entry point stays src/proxy.ts. Passing a bounded QA flow does not resolve Free CPU capacity or authorize this different QA adapter path for Production.
